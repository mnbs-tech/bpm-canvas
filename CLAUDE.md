## What this is

A Next.js (App Router) swimlane/BPM workflow diagram editor built on React Flow
(`@xyflow/react`), for back-office processes (見積/契約/請求/更新 etc.). Deployed at
`https://ai.mnbs.net/workflow` behind nginx, gated by Cognito Hosted UI login, running
as a systemd service on `127.0.0.1:8002`. There is no test suite — verification is
`tsc --noEmit` + `next build` + `eslint`, plus manual/Playwright-driven browser checks.

### Versioning rule

Every commit bumps `package.json`'s `version` (semver `MAJOR.MINOR.PATCH`) — one commit
per version bump, no batching unrelated changes into a single commit without one:

- Bug fix or minor improvement (small tweak, not a new feature) → bump **PATCH**
  (`1.0.0` → `1.0.1`)
- Feature addition → bump **MINOR**, reset PATCH to 0 (`1.0.1` → `1.1.0`)
- Explicit user instruction to mark a milestone → bump **MAJOR**, reset MINOR/PATCH to 0
  (`1.9.0` → `2.0.0`). This is never automatic (no more rollover past `.9`) — it happens
  only when the user explicitly asks for a MAJOR bump.

A version bump also adds its entry to `src/lib/changelog.ts`, in the same commit — that
array is what the ⚙️ menu's 変更履歴 dialog renders (SPEC §3.21). Entries are hand-written
Japanese aimed at the user, not the English commit subject. An entry carries no `version`
only when the change genuinely shipped without one (everything before `1.2.0`, where
version management began, plus the few later commits that landed without a bump) — those
are identified by date. Nothing reads git at runtime; the backfilled entries carry their
`commit` hash so they can still be traced.

The AI chat feature (`1.2.0` → `2.0.0`) was an explicit user-requested MAJOR bump for
that milestone — an example of the MAJOR case above, not a `.9` rollover (the rollover
rule no longer applies).

### Deploying a change

```bash
npm run build
sudo systemctl restart workflow-builder.service
```

`systemd/workflow-builder.service` and `nginx/workflow-builder.location.conf` are the
source of truth, symlinked into `/etc/systemd/system/` and `/etc/nginx/snippets/`
respectively — edit the repo copy, not the symlink target. After editing the systemd
unit, `sudo systemctl daemon-reload` is required before `restart` picks it up. After
editing the nginx conf, `sudo nginx -t && sudo systemctl reload nginx`.

`secrets.env` (gitignored, holds `COGNITO_CLIENT_SECRET`/`COGNITO_DOMAIN`) is loaded via
the systemd unit's `EnvironmentFile=-...` (the leading `-` makes it optional, so the
service still starts — with auth as a passthrough — if the file is missing).

### The release kit

`npm run kit` (`scripts/build-release-kit.sh`) zips this app's source into
`dist/workflow-builder-kit-v<version>.zip`, which the ⚙️ menu offers as a download
(`/api/release-kit` reports whether one exists, `/api/release-kit/download` serves it).
Someone unzips it on their own PC and follows `docs/LOCAL_RUNBOOK.md`: `WORKFLOW_AUTH=off`
plus `WORKFLOW_STORAGE=local` turn the same code into a single-machine install.

**Build a kit only when a human explicitly asks for one.** It is deliberately not part of
`npm run build`, the deploy, or any commit hook. The archive on the server is a published
artifact — whatever is in `dist/` is what people download and run, and it keeps being
served long after the build that made it. Nobody should discover a new version was
distributed because an agent tidied up. Concretely: don't run `npm run kit` to "check that
it works" after touching this code, and don't add it to a build step.

Contents come from `git archive HEAD`, which is what makes the archive safe rather than a
maintained exclusion list: only committed, tracked files ship, so `secrets.env` and
`.htpasswd` (gitignored) cannot leak in. `.gitattributes` `export-ignore` drops `systemd/`
and `nginx/` on top of that — this host's paths and Cognito ids, useless and misleading on
a PC. Because it archives `HEAD`, uncommitted edits are not in the kit; the script warns
when the tree is dirty rather than silently shipping the last commit.

Two things to keep together: `env.local.example` (the file the runbook tells people to copy
to `.env.local` — no leading dot, since `.gitignore` excludes `.env*` and it must be
tracked to reach the archive) and the env vars `docs/LOCAL_RUNBOOK.md` documents. A new
setting a local install needs is a change to both.

To test changes without touching the live authenticated service, run a throwaway
instance on another port with Cognito env vars unset (falls back to an auth passthrough
— see `isCognitoConfigured()` in `src/lib/cognitoAuth.ts`):

```bash
env -u COGNITO_REGION -u COGNITO_USER_POOL_ID -u COGNITO_CLIENT_ID \
    -u COGNITO_CLIENT_SECRET -u COGNITO_DOMAIN \
    node node_modules/.bin/next start -H 127.0.0.1 -p 8099
```

The same trick exercises what a local install actually runs — the auth switch and the
folder backend — without an AWS call or a second checkout:

```bash
WORKFLOW_AUTH=off WORKFLOW_STORAGE=local WORKFLOW_DATA_DIR=/tmp/wf-data \
    node node_modules/.bin/next start -H 127.0.0.1 -p 8099
```

## Architecture

### Document model (`src/lib/types.ts`)

`WorkflowDocument` is the JSON format saved to S3 / exported locally: `{ formatVersion,
id?, name, orientation, lanes, nodes, edges, subflows?, updatedAt }`. `public/workflow-format.md`
is the full schema reference (also downloadable from the app's build-info footer) —
read it instead of re-deriving the format from the node components.

**Orientation is a coordinate-system flip, not just a CSS change.** `orientation:
"horizontal"` (the default) means lanes are rows stacked in `y`, flow runs left→right
along `x`. `"vertical"` swaps that: lanes are columns in `x`, flow runs top→bottom in
`y`. Toggling it transposes every node's `{x,y}` (self-inverse, lossless) and rotates
every node's `Handle` positions via `rotatedPosition()` in `src/lib/orientation.tsx`
(`OrientationContext`) — every node component under `src/components/nodes/` calls
`useOrientation()` + `rotatedPosition()` for its `Handle` `position` props. `node.position`
is always the node's **top-left corner**, never its center — layout code that centers a
node in its lane must subtract half its footprint (see `NODE_SIZE` in `autoLayout.ts`).

**Subflows** (`type: "subflow"` nodes) point at a nested `{nodes, edges}` graph stored in
the document's top-level `subflows` map, keyed by `data.subflowId`. Only one flow is
ever "live" in React state at a time (`WorkflowEditor.tsx`'s `nodes`/`edges` +
`currentFlowId`); navigating in/out via `SubflowNavContext` stashes the outgoing flow
into a `flows` map and loads the target — see `navigateTo`/`snapshotAllFlows` in
`WorkflowEditor.tsx`.

**Edge style must be set explicitly**, via the `EDGE_STYLE` constant in `types.ts`, on
every edge created anywhere (`onConnect`, `templates.ts`, hand-authored JSON). React
Flow's default edge stroke comes from a CSS custom property that `html-to-image` doesn't
resolve when capturing for PDF/clipboard export, so an edge without an explicit inline
`style` renders invisibly in exports even though it looks fine on screen. The same class
of bug hit `DatabaseNode`'s raw SVG shape (Tailwind `fill-*`/`stroke-*` classes on
`<path>`/`<ellipse>` silently don't survive export) — any new SVG-based node visual
needs inline `style` colors, not Tailwind classes, for the same reason.

### Layout (`src/lib/autoLayout.ts`)

"自動整列" re-flows nodes along the process axis while preserving each node's current
lane: rank = longest-path from a topological sort (Kahn's algorithm; a cyclic graph
degrades gracefully by appending leftover nodes rather than looping), lane assignment
comes from each node's current position on the lane axis. `templates.ts` reuses this —
templates only declare a lane index and edge topology per node, then call
`autoLayoutNodes` to compute actual coordinates.

### Storage (S3 or a local folder)

`src/lib/objectStore.ts` picks a backend from `WORKFLOW_STORAGE`; `s3ObjectStore.ts` and
`fsObjectStore.ts` implement it; `workflowStore.ts` holds everything above it (keys, the
index manifest, version ids, pruning) and `src/app/api/workflows/**/route.ts` sits on top
of that. **The split exists so a copy can run on someone's own PC** with no AWS account
(the release kit, below) — not as a general-purpose abstraction, which is why the
interface is four methods (`get`/`put`/`remove`/`list`) and nothing more.

**Both backends use the same keys**, so a data directory and a bucket prefix are the same
bytes in the same shape and `aws s3 sync` moves a whole installation either way. Anything
that changes the key layout has to stay backend-agnostic and live in `workflowStore.ts`.

S3: bucket `bucket-yn1ubx` in **`ap-northeast-1`** — the AWS SDK v3 client's region must
match exactly; unlike `boto3`, it does not transparently follow S3's cross-region
redirect. Credentials come from the EC2 instance's IAM role (no explicit credential
config). The client is constructed lazily so the local backend never builds one.

Local (`WORKFLOW_STORAGE=local`, rooted at `WORKFLOW_DATA_DIR`): keys become paths, writes
go through a temp file and `rename` (an interrupted save must not truncate `_index.json`,
which would read as "no saved flows"), and keys are re-checked against the root before
becoming a real path — `isSafeId()` already ran, but this backend writes to the
operator's filesystem rather than into a bucket prefix.

Listing is backed by a single `_index.json` manifest under the `workflow-builder/flows/`
prefix (read-modify-write on every save/delete, not locked — acceptable for this
internal tool's traffic).

Every save also writes a snapshot under `workflow-builder/versions/<flow id>/<version id>.json`
(newest 30 kept, pruned on save; deleted with the flow). This is **not** S3 bucket versioning:
the bucket is shared with claude-dashboard, versioning is bucket-wide and can only be
suspended once enabled, and this instance's role cannot even call `s3:GetBucketVersioning`
(verified: AccessDenied). Version ids lead with a compact UTC timestamp so S3's lexical key
order is save order — that is what `listVersions` sorts on and what pruning slices. Snapshot
failures are logged and swallowed: history must never fail the save it belongs to. Ids reaching
`workflowStore` from URL segments go through `isSafeId()` first, since they are pasted into
storage keys.

Client-side code must prefix API calls with `BASE_PATH` (`src/lib/basePath.ts`,
`"/workflow"`, kept in sync with `next.config.ts`'s `basePath`) — unlike `next/link` and
the router, a plain client `fetch("/api/...")` does not get the basePath prepended
automatically.

### Auth (`src/lib/cognitoAuth.ts`, `src/proxy.ts`, `src/app/auth/*/route.ts`)

Cognito Hosted UI OAuth2 login, ported from claude-dashboard's `app/cognito_auth.py`
pattern. Shares the same Cognito App Client and session cookie name (`cd_session`) as
claude-dashboard/s3manager on this host, so logging into one signs you into all three.
Gate is enforced in `src/proxy.ts` (Next.js 16 renamed `middleware.ts` → `proxy.ts`,
exported function is `proxy` not `middleware`), which passes through when Cognito env
vars aren't set rather than failing closed (see `isCognitoConfigured()`'s doc comment —
gating before Cognito is actually configured would redirect-loop to a domain that
doesn't resolve).

`WORKFLOW_AUTH=off` turns the gate off on purpose (`isAuthEnabled()`), which is what a
copy on someone's own PC runs with. It is a **separate switch from the unconfigured
passthrough on purpose**: "no Cognito vars" equally describes a server whose `secrets.env`
went missing, so an operator reading a log or a unit file can't tell an intended open door
from an accident — `WORKFLOW_AUTH=off` is unambiguous. With the gate off, `/auth/login`
and `/auth/logout` redirect home instead of building a Hosted UI URL out of an empty
`COGNITO_DOMAIN` (a relative URL, which `NextResponse.redirect` throws on — a 500 on a
documented endpoint in a supported configuration).

Two version-specific pitfalls already hit here, worth checking for regressions on any
Next.js upgrade: the documented "exclude `_next/static` et al" negative-lookahead
`matcher` pattern silently never matched the bare basePath root (`proxy.ts` uses an
unconditional `/:path*` instead); and `request.nextUrl.origin` is unusable for
post-login redirects behind this nginx setup because Next.js normalizes any `127.x.x.x`
connection host to the literal string `"localhost"` (`postLoginRedirectUrl()` derives
the target from `COGNITO_REDIRECT_URI` instead).

### Export (`src/lib/exportImage.ts`)

PDF export and clipboard-copy both go through `captureFlowImage()`: snap the live
viewport to frame all nodes via `getViewportForBounds`, capture the wrapper div with
`html-to-image`, restore the original viewport. `getViewportForBounds`'s `padding`
argument is a **fraction** of the viewport when given a bare number, not pixels — always
pass a `"Npx"` string (see the comment on the `PADDING` constant); this bug previously
produced tiny, mostly-blank exports.

### Excel export (`src/lib/excelDrawing.ts`, `exportExcel.ts`)

Excel is the one export that does **not** go through `captureFlowImage()`. It used to,
and the picture it pasted was the complaint: the recipient could not move a step or
retype a name. Each sheet is now rebuilt from the graph as native Excel shapes.

- **exceljs has no shape API** — only images. So `excelDrawing.ts` emits the DrawingML
  itself (a pure `graph -> string` function, no DOM, no exceljs), and `injectDrawings()`
  in `exportExcel.ts` opens the workbook exceljs wrote with jszip and adds the four parts
  a drawing needs: `xl/drawings/drawingN.xml`, the sheet's `_rels` entry, the
  `<drawing r:id>` element at the end of the sheet, and the `[Content_Types].xml`
  override. Sheets are found through `xl/workbook.xml` + its rels, never by assuming
  `sheet1.xml` is the first sheet.
- **Connectors are `bentConnector3` elbows, routed to suit that preset.** Its path is
  fixed at horizontal→vertical→horizontal, so lines must leave and arrive *sideways*:
  `connectorPoints` uses side anchors whenever the two shapes are clear of each other
  horizontally (any lane change) and bottom-to-top only when they overlap in the same
  column. Rotating the connector 90° to get a vertical→horizontal→vertical elbow was
  tried and abandoned — the lines rendered nowhere near their shapes. Gluing lines to
  shapes (`stCxn`/`endCxn`) is also avoided: the connection-site index differs per preset
  geometry and a wrong one makes Excel prompt to repair the file.
- **A shape's `name` attribute must not contain a newline.** It is built from the step
  label, which is free text and often multi-line; a raw newline there made Excel offer to
  repair the file on open. XML *normalises* rather than rejects it, so the file parses and
  LibreOffice is perfectly happy — `shapeName()` collapses whitespace and strips control
  characters.
- **Anchors must be `twoCellAnchor` with real row/column indices.** A `oneCellAnchor`
  pinned to A1 that carries the whole position in `colOff`/`rowOff` renders perfectly in
  LibreOffice and **breaks in Excel**: shapes keep their size but collapse toward the
  top-left corner. Excel only ever writes offsets that fall *inside* the anchor cell, so
  `cellRef()` converts px to (col, colOff, row, rowOff) against the default grid — a
  15pt row is 20px, a default column is 64px.
- **Verifying it without a browser**: `buildWorkbookBuffer()` is split out of
  `exportPagesToExcel()` for exactly this — it touches no browser API, so a small Node
  script can generate a real `.xlsx`. Open it with `soffice --headless --convert-to pdf`
  (needs the `libreoffice-calc` package; without it LibreOffice fails to load *any*
  xlsx, including Excel's own, which looks misleadingly like a bad file) and check every
  part parses and every shape id is unique.
- **LibreOffice rendering is necessary but not sufficient.** It accepts anchor geometry
  Excel rejects — the bug above shipped because the LibreOffice render looked right. When
  changing anchors or geometry, also assert the *invariants Excel relies on* (offsets
  smaller than one cell, monotonic col/row indices) rather than trusting the picture, and
  compare against a real Excel-authored file when one is available.
- **Real saved flows make the best test data**, and they are reachable from this host:
  the documents live at `s3://bucket-yn1ubx/workflow-builder/flows/<id>.json` and can be
  fetched with a short script using the bundled `@aws-sdk/client-s3`. Note a saved doc may
  be `orientation: "horizontal"`; the toolbar's 縦 toggle transposes x/y on every flow
  (`handleToggleOrientation`), so a harness must do the same to reproduce what the user
  exported.

### UI structure

`WorkflowEditor.tsx` is the orchestrator (all editor state, all handlers), composing
`Toolbar` (top bar), `Sidebar` (node palette + swimlane list, collapsible, left), the
canvas (`LaneBackground` absolutely-positioned behind a `ReactFlow` instance), and
`ChatPanel` (AI chat, collapsible, right — see below). Node components live under
`src/components/nodes/`, registered in `nodes/index.ts`'s `nodeTypes`, and declared in
`src/lib/nodeDefs.ts`'s `NODE_PALETTE` (drag source for the sidebar). Adding a new node
kind touches all three plus `types.ts`'s `NodeKind` union.

**Dropdowns are placed by measurement, not by class** (`src/lib/dropdownPlacement.ts`,
used by `Toolbar`'s 整列/保存 menus and `AppInfoMenu`). The toolbar is `flex-wrap`, so on a
phone its buttons end up on rows the alignment was never chosen for: a `right-0` menu on a
button that has wrapped to the left edge extends past `x=0`, and nothing clips or scrolls
it back — it is simply not on screen, which reads as "the menu doesn't open" rather than
"the menu is misplaced". `useDropdownPlacement(open, align)` keeps the class as the
preferred placement and clamps the measured box into the window (`useLayoutEffect`, so it
lands before paint).

Destructure its return (`const { anchorRef, menuRef, style } = ...`) instead of holding the
object: reading `menu.anchorRef` in JSX trips `react-hooks/refs` ("Cannot access refs
during render"), the same rule described under Notifications and dialogs below.

### Selection operations (`src/lib/cloneSelection.ts`, `src/lib/alignNodes.ts`)

Copy/paste/duplicate and align/distribute are pure functions over node arrays,
like `autoLayout.ts` - `WorkflowEditor` only holds the clipboard (a ref, not the system
clipboard: what is copied is document structure, not text) and feeds state in and out.
Copying a `subflow` node clones its whole nested graph under a fresh `subflowId`,
recursively, because two nodes pointing at one subflow is undefined per SPEC §3.6 - and
would silently make editing the copy edit the original.

Arrow-key nudging is **not** implemented here: React Flow already moves the selected
nodes (5px, 20px with Shift) from a focused node's `onKeyDown`, and clicking a node
focuses it. Adding a window-level arrow handler would double-move for that case.

### Notifications and dialogs (`src/lib/toast.tsx`, `src/lib/dialog.tsx`)

No `window.alert` / `confirm` / `prompt` anywhere in `src/` — both are rendered in-app,
mounted as providers in `src/app/page.tsx` (toasts outermost, so a dialog can raise one
and have it paint above the dialog's backdrop). `useToast().show(message, kind)` for
results nothing waits on; `useDialog().confirm()/prompt()` return promises, so the
callers that used to branch on a synchronous `confirm()` are now `async` — check that
when adding a destructive action.

The one shape to keep: a component reading its own `.current` in a `useCallback` is
fine, but **if that callback ends up in a `useMemo`'s dependency array, the memo counts
as ref-derived and reading its value during render is a `react-hooks/refs` lint error**
("Cannot access refs during render", reported at the render-time read, not at the ref).
That is why `openEdgeLabelEditor` (a dependency of `menuItems`, which the JSX reads)
takes an already-computed anchor point instead of measuring the wrapper itself.

### AI chat (`src/components/ChatPanel.tsx`, `src/app/api/chat/route.ts`, `src/lib/chatService.ts`)

Lets the user ask an AI to evaluate/discuss the workflow they're currently editing,
right next to the canvas rather than in a separate tool. `ChatPanel` mirrors `Sidebar`'s
collapsible-`<aside>` pattern but on the right edge, and holds its own message history
client-side (nothing is persisted server-side; a reload loses the conversation, same as
unsaved canvas edits). On send it calls `WorkflowEditor.tsx`'s `getWorkflowSnapshot()` —
the same `WorkflowDocument` shape `handleSave` builds via `snapshotAllFlows()`, captured
fresh at send-time, not once at mount — and POSTs `{ messages, workflow }` to
`/api/chat`.

The route hands off to `chatService.askWorkflowAssistant()`, which shells out to `claude
-p --restricted --output-format text --no-session-persistence` (pattern lifted from
claude-dashboard's `report_generator.py`) with the whole conversation transcript plus
the workflow JSON embedded in one prompt — `claude -p` is stateless per call, so
multi-turn context has to be replayed in full each time rather than resumed.
`--restricted` strips Bash/code-execution tools and WebFetch since everything the model
needs is already in the prompt; no file access is required or granted.

Two things must move together if either changes (they cover both chat routes —
`/api/chat` and `/api/chat/proposal` share `runClaude()`): `chatService.ts`'s `CHAT_TIMEOUT_MS`
must stay below the `proxy_read_timeout`/`proxy_send_timeout` set on the `/workflow`
nginx location, or a slow turn surfaces as a bare nginx 504 instead of this app's own
timeout error. And per the global CLAUDE.md's systemd-PATH pitfall, `claude` lives at
`~/.local/bin/claude`, outside systemd's default `PATH` — `workflow-builder.service`
sets `PATH` explicitly for exactly this reason; removing that line breaks the chat
feature with a silent `ENOENT` (works fine under `npm run dev` in an interactive shell,
which is why this is easy to miss until the systemd-managed instance is tested).

### Applying an AI proposal (`src/lib/proposalSchema.ts`, `applyProposal.ts`, `ProposalBanner.tsx`)

"この提案を図に反映" turns the last chat answer into edits the user can see before
accepting. Three deliberate choices shape it:

**A diff, not a regenerated document.** The model returns `{summary, operations}` —
add/update/remove per node and edge, scoped by `flowId`. Handing back a whole rewritten
`WorkflowDocument` would silently drop everything the model didn't think to repeat, and
there would be nothing to render as "this is what changes". Ids the model invents for new
nodes are references only: `applyProposal` swaps them for uuids, so a proposal can never
collide with a saved id, and an `addEdge` can point at a node added in the same diff.

**A second `claude -p` call, not a JSON-shaped chat.** The conversation stays prose;
`proposeWorkflowEdit()` replays the same transcript with the schema and asks for JSON only
(`parseProposalText` still tolerates a stray fence or preamble). The structured turn is
paid for only when the user presses the button.

**Positions are computed here, not asked for.** `placeAddedNodes` puts a new node one
`RANK_GAP` past its upstream neighbour, in the lane the model named (or its neighbour's),
nudging along the lane axis when the slot is taken. It deliberately does *not* call
`autoLayoutNodes`: re-flowing the graph would move nodes the proposal never mentioned,
which is the opposite of a reviewable diff. That is why `nodeFootprint`/`laneIndexOfNode`
are exported from `autoLayout.ts` — both files must read lanes the same way.

`applyProposal` returns two documents: `doc` (what gets committed) and `preview` (the same
thing with removals put back and marker classes on everything touched). Only `doc` is ever
saved. The markers are CSS-only (`.proposal-add/-update/-remove` in `globals.css`), so no
node component knows previews exist; edges are marked by inline `style` instead, for the
same html-to-image reason `EDGE_STYLE` exists.

**The preview is a document the user has not accepted, and every path that persists state
has to be held off while it is on screen.** This is the part that bites:

- The history hook's suppress window (`suppressDirtyUntilRef`) is refreshed by an interval
  for as long as the preview lasts — a preview lasts as long as someone takes to read it,
  far longer than the fixed 800ms windows the rest of the editor uses. Without it the
  marked-up copy becomes an undo step.
- `recordNow` takes an *explicit* snapshot when accepting: `currentRef` inside the history
  hook is the marked copy by then, so the undo step has to be the state captured before the
  preview started.
- The draft writer (`writeDraft`) skips while previewing, or a later session would offer to
  restore the AI's suggestion as the user's own unsaved work.
- The canvas is read-only (`nodesDraggable`/`nodesConnectable`/`deleteKeyCode`, the context
  menu, the details panel), the editor shortcuts return early, and `Toolbar` wraps its
  action group in `<fieldset disabled className="contents">` — `display: contents` keeps the
  flex layout while the fieldset's `disabled` reaches every control inside it.
- `ChatPanel` stops sending: `getWorkflowSnapshot()` returns the *marked* document while a
  preview is up, which is not what the AI should be shown (and not what should be saved).

One layout note: entering a preview fits the view twice — `putDocument`'s own
`requestAnimationFrame` pass, then a deferred one, because the banner appears in the same
commit and takes a strip off the top of the canvas that React Flow only measures a beat
later. And if nothing in the flow on screen changes, the preview navigates to the flow that
does change; otherwise a subflow-only proposal previews as a canvas where nothing happens.
